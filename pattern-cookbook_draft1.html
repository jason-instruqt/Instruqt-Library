Preface

This book is the recipe form of a working library. Every pattern here has been used in a production track, hit a problem, been refined, and come back to be used again. The names are the names that authors use when they describe what they built to other authors. The shapes are the shapes that survive contact with real learners on real labs.

The book is organized for the moment you have a problem in front of you. Each recipe is self-contained. You can read one and act on it without reading the rest of the book. The pieces are small on purpose: when something is broken at four o'clock on a Friday before a Monday demo, you do not have time to read three chapters.

The companion book is The Instruqt Track Builder's Field Guide, which walks the lifecycle of a track end to end and explains the reasoning behind the patterns. The Field Guide teaches you how to think about a track. This Cookbook tells you exactly what to type. The two are best read together — Field Guide first, Cookbook on the desk afterwards — but each works on its own.

Three constraints shape every recipe. No real track names appear anywhere. The patterns are described concretely enough that the reader can implement them from the description alone. Code is like-for-like, not verbatim. Hostnames, image references, and identifiers are generic placeholders that mirror the structure of real production code without copying it. Voice is direct. When a pattern has a known failure mode, the failure mode is named and the symptom is named. When an opinion is earned, the opinion is given without softening.

—

How to Read This Book

The Cookbook is structured as recipes. Each recipe is a single, complete, copy-friendly answer to a specific design problem. You can read it cover to cover, but it is built to be opened to one page when you have a problem in front of you.

Every recipe follows the same six-section format:

  • Use when — a one-line guidance test. If this line does not match your situation, skip the recipe.
  • Problem — the situation that prompts the pattern. What you tried first, why it did not work, what the failure looked like.
  • Solution — the conceptual shape of the answer. The mental model, in prose, before any code.
  • Skeleton — copy-friendly code or YAML. Generic names; safe to lift and adapt.
  • Gotchas — the failure modes other authors have hit. Specific symptoms, specific fixes.
  • Variations — related recipes, alternative shapes, or extensions worth knowing about.

Patterns are categorized by scope. Infrastructure patterns describe how a track's hosts, networks, and resources are wired together — decisions that live in config.yml. Technique patterns describe a single self-contained move. Author patterns describe how content is structured and presented to the learner — decisions that live in assignment.md files.

Recipes are numbered globally and continuously. Cross-references in the text use the recipe number.

R 01
Part II — Infrastructure

Single container track

InfrastructureBasic
Use when The track demonstrates command-line work that fits inside one Linux container with no other infrastructure.
PROBLEM

A track for a CLI tool, a scripting walkthrough, or a self-contained tutorial does not need a database, a VM, or a cloud account. The standard temptation is to reach for a bigger shape than the problem requires — multi-container, container-plus-VM, full sandbox — because the bigger shapes feel more "real." They are slower, cost more lab-session compute, and add failure modes the lesson does not teach. Single-container is almost always the right shape when one host is enough.

SOLUTION

Declare one container in config.yml, give it a sensible name, point it at one of the platform's base images, and stop. Use a single terminal tab. Put any tooling the lesson needs into the track-level setup script.

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    memory: 1024
    shell: /bin/bash
bashtrack_scripts/setup-workstation
#!/bin/bash
set -euxo pipefail

apt-get update -qq
apt-get install -y -qq jq tree
yamlassignment.md (tabs)
tabs:
  - title: Terminal
    type: terminal
    hostname: workstation
GOTCHAS

The default base image is gcr.io/instruqt/shell — minimal, ~100 MB, no cloud CLIs. The heavier gcr.io/instruqt/cloud-client ships with aws, gcloud, az, kubectl, and helm preinstalled and is roughly 1.5 GB. Use the lighter one for pure-bash and pure-CLI lessons; use the heavier one when even one cloud CLI would otherwise need to be installed in setup.

The default shell when no cmd: is set on the terminal tab is /bin/bash running as root. If the lesson teaches non-root workflows, see Recipe 29.

The memory: field is in megabytes. 1024 is enough for almost any single-container track that does not run a database, a JVM, or a model. Bump to 2048 only after measuring.

VARIATIONS

For tracks that demonstrate a tool the platform's base images do not ship, build a custom container image and reference it from config.yml. Cache pulls with Recipe 20 to keep boot times low.

For tracks that need no custom infrastructure at all, see Recipe 6 (sandbox preset adoption), which lets you skip config.yml entirely.

R 02
Part II — Infrastructure

Single VM track

InfrastructureBasic
Use when The track needs a real Linux kernel, a display server, custom kernel modules, systemd, or any workload that does not run inside a container.
PROBLEM

Containers are fast to boot, cheap to run, and sufficient for most tracks. They are not sufficient when the lesson involves systemd unit files, kernel-module loading, real network namespaces beyond what a container can simulate, or any GUI workload that requires a display server. Trying to teach those things inside a container is a long fight with workarounds; teaching them on a VM is the path of least resistance.

SOLUTION

Declare one VM in config.yml, use the platform's stock Ubuntu image (or a custom image if you have one), and provision tooling in the VM's track-level setup script. Surface a terminal tab pointing at the VM.

SKELETON
yamlconfig.yml
version: "3"
virtualmachines:
  - name: workstation
    image: ubuntu-2204
    machine_type: n1-standard-2
    shell: /bin/bash
yamlassignment.md (tabs)
tabs:
  - title: Terminal
    type: terminal
    hostname: workstation
GOTCHAS

VM boot takes 60–120 seconds compared to a container's 5–15. Set learner expectations accordingly: the first challenge's loading message should mention that the environment is provisioning. See Recipe 21 (bootstrap wait) for the pattern that protects setup scripts from running before the host is fully up.

VMs cost more per lab-session than containers. Default to a container; reach for a VM only when the track genuinely needs one.

The machine_type: field accepts standard GCP machine types. n1-standard-2 (2 vCPU, 7.5 GB RAM) is a sensible default. Step up to n1-standard-4 only when you have measured a workload that needs it.

VARIATIONS

For tracks that need a desktop UI on the VM, see Recipe 17 (noVNC) or Recipe 16 (Guacamole). For a single GUI application without a full desktop, see Recipe 18 (KasmVNC).

For tracks that need a VM running Docker — a meta-pattern where the VM hosts containers — see Recipe 19.

R 03
Part II — Infrastructure

Multi-container composition

InfrastructureIntermediate
Use when The lesson involves two or more services that need to talk to each other over a network — typically an application and a backing service like a database, message queue, or cache.
PROBLEM

A workstation container is enough for command-line teaching. Once the lesson involves a real application and that application talks to a database or a queue, a single container starts fighting itself. Running both processes in one container means juggling supervisord or background processes, and the failure modes leak into the lesson. The clean shape is one process per container, wired together by hostname.

SOLUTION

Declare each service as its own container in config.yml. Use container names as the hostname for inter-service communication. Set environment: keys on each container to pass connection strings or service URLs. The platform creates a Docker network that all declared containers share, so any container can reach any other by its declared name.

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    ports: [8080]
    memory: 1024
    shell: /bin/bash
    environment:
      DB_HOST: db
      QUEUE_URL: redis://queue:6379
  - name: db
    image: postgres:16
    ports: [5432]
    memory: 1024
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
  - name: queue
    image: redis:7-alpine
    ports: [6379]
    memory: 256
GOTCHAS

Containers boot in parallel, not in dependency order. The workstation's setup script may start before postgres or redis is ready to accept connections. Always poll for readiness — pg_isready -h db for postgres, redis-cli -h queue ping for redis — before any setup that depends on the service. See Recipe 22 for the general wait-for-port pattern.

The learner's browser cannot resolve internal Docker hostnames. If the workstation serves a web UI on port 8080 and that UI's JavaScript calls fetch('http://api:5000/data'), the fetch fails because the browser is talking to the Instruqt proxy, not the Docker network. Always use relative paths in client-side code; route everything through one service tab.

The ports: field declares which ports the platform should be aware of for service-tab purposes. It does not restrict which ports the container can use internally.

VARIATIONS

For a workstation paired specifically with postgres and a live web dashboard, see Recipe 14. For a workstation paired with a FastAPI service, see Recipe 12. For a workstation paired with a mock REST API and a branded CLI, see Recipe 13.

R 04
Part II — Infrastructure

Multi-VM composition

InfrastructureIntermediate
Use when The lesson involves two or more full Linux hosts that need to be addressable by hostname — typically when teaching distributed systems, replication, clustering, or anything where the boundary between hosts is part of the lesson.
PROBLEM

Multi-container is the right shape for application-plus-database. It is not the right shape for "set up replication between primary and replica," "configure a load balancer in front of two app servers," or "join this node to a cluster." Those lessons need real network boundaries between real hosts, and the only way to get that on the platform is multi-VM.

SOLUTION

Declare each VM in config.yml with a distinct name. The platform places all declared VMs on a shared private network and registers each name in DNS. From any VM, any other VM is reachable by its declared name. Surface a terminal tab per VM, or use one workstation VM and SSH between hosts during the lesson.

SKELETON
yamlconfig.yml
version: "3"
virtualmachines:
  - name: primary
    image: ubuntu-2204
    machine_type: n1-standard-2
    shell: /bin/bash
  - name: replica
    image: ubuntu-2204
    machine_type: n1-standard-2
    shell: /bin/bash
  - name: client
    image: ubuntu-2204
    machine_type: n1-standard-1
    shell: /bin/bash
yamlassignment.md (tabs)
tabs:
  - title: Primary
    type: terminal
    hostname: primary
  - title: Replica
    type: terminal
    hostname: replica
  - title: Client
    type: terminal
    hostname: client
GOTCHAS

Three VMs is the limit at which the lab boot time becomes uncomfortable for the learner. Past three, expect 90+ seconds of provisioning even with everything cached. Use multi-VM judiciously; consider whether two VMs plus a workstation container can cover what three full VMs would cover.

Each VM's setup script runs independently on its host. There is no implicit ordering. If the replica's setup needs the primary to already be running, use Recipe 34 (agent variable cross-host hand-off) to gate the replica on a signal from the primary.

SSH between VMs is not preconfigured. If the lesson requires it, generate a key on one VM, copy the public key to the others' authorized_keys files in setup, and document the convention.

VARIATIONS

For a hybrid where one host is a container (the workstation) and the others are VMs (the systems being managed), see Recipe 5.

For a multi-VM cluster where the lesson centers on a control plane, dedicate one VM as the control plane and use it as the primary terminal tab; the other VMs become objects of management.

R 05
Part II — Infrastructure

Container plus managed VM

InfrastructureIntermediate
Use when The lesson is about operating a VM — installing software on it, configuring services on it, troubleshooting it — and the learner should manage it from a separate workstation.
PROBLEM

A single-VM track puts the learner directly on the VM, which collapses two things that are usually distinct in real operations: the operator's workstation and the system being operated. For lessons where the distinction matters — SSH workflows, configuration management with ansible or terraform, log forwarding, anything where "from where" is part of the story — the learner needs a separate place to run commands from.

SOLUTION

Declare one container as the workstation (where the learner types) and one VM as the managed host (the object of the lesson). Surface the workstation as a terminal tab. Put SSH credentials on the workstation in setup so the learner can ssh managed-host without ceremony.

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    memory: 1024
    shell: /bin/bash
virtualmachines:
  - name: managed-host
    image: ubuntu-2204
    machine_type: n1-standard-2
    shell: /bin/bash
bashtrack_scripts/setup-workstation
#!/bin/bash
set -euxo pipefail

# Generate keypair on workstation, push public key to managed-host
ssh-keygen -t ed25519 -N "" -f /root/.ssh/id_ed25519
PUBKEY=$(cat /root/.ssh/id_ed25519.pub)
agent variable set MANAGED_HOST_PUBKEY "$PUBKEY"
bashtrack_scripts/setup-managed-host
#!/bin/bash
set -euxo pipefail

mkdir -p /root/.ssh
chmod 700 /root/.ssh
PUBKEY=$(agent variable get MANAGED_HOST_PUBKEY)
echo "$PUBKEY" >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
GOTCHAS

The container boots faster than the VM. The workstation's setup will likely complete before the VM is ready; do not have the workstation try to SSH into the managed host during setup unless you have explicitly waited. The agent variable round-trip in the skeleton above is one safe synchronization point — the managed-host setup script will not finish until the variable is read.

A learner who can SSH into the managed host as root has the keys to the kingdom. If the lesson is about permissions, drop into a non-root user on the managed host (Recipe 29) and grant SSH only to that user.

VARIATIONS

When the managed host should not have a public IP — for example, a Compute Engine instance that should appear "private" — see Recipe 11 (IAP tunnel).

For multi-host scenarios where the workstation manages several VMs, scale this pattern up: declare more VMs, push the workstation's public key into each one, document the hostnames in the assignment.

Sandbox preset adoption

InfrastructureBasic
Use when The lesson does not need any custom infrastructure beyond what a vendor or the platform pre-bakes.
PROBLEM

Most tracks declare custom infrastructure in config.yml. Some do not need to. A pure introductory walkthrough, a documentation-style lesson, or a track that demonstrates a SaaS product where the learner does all their work in the vendor's web UI may have nothing to declare. Building a config.yml for a track that does not need one wastes boot time and creates infrastructure surface for no benefit.

SOLUTION

Use a sandbox preset — a pre-baked environment offered by the platform or a vendor partner. Reference the preset in track.yml's sandbox_preset_id field and omit config.yml entirely. The platform handles provisioning the preset's resources.

SKELETON
yamltrack.yml (excerpt)
slug: introductory-walkthrough
title: Introductory walkthrough
sandbox_preset_id: <preset-uuid-from-platform>
lab_config:
  layout: default
GOTCHAS

Preset hosts have fixed names defined by the preset. Lifecycle scripts must be named to match (e.g., setup-workstation if the preset's host is named workstation). The preset's documentation lists the host names; do not guess.

Sandbox presets are versioned. Updates to the preset by its maintainer can break tracks that depend on its exact behavior. When using a preset built by another team, pin the version explicitly if pinning is supported.

A track that uses a preset cannot also declare custom containers or VMs in config.yml. The two are mutually exclusive at the track level.

VARIATIONS

For tracks that demonstrate a vendor product with a published preset, the preset is almost always the right starting point. Build the lesson on top of the preset rather than recreating its environment.

For tracks that need almost the preset but with one tweak, do not use the preset; reconstruct what it provides in your own config.yml. The preset's compatibility envelope is too narrow to bend reliably.

Container plus AWS account

InfrastructureIntermediate
Use when The lesson involves real AWS resources — IAM, S3, EC2, Lambda, anything that lives in an AWS account — and the learner needs to operate against a real account they did not bring themselves.
PROBLEM

You cannot teach AWS effectively against a static screenshot. Real AWS lessons need a real AWS account: real aws CLI, real console login, real API responses. Asking the learner to bring their own account is hostile to onboarding flow and prevents you from constraining the lab to a known scope.

SOLUTION

Declare an aws_accounts block in config.yml. The platform provisions a fresh AWS account, scopes IAM as you specify, and tears it down at the end of the lab. Pair it with a workstation container that has the aws CLI preinstalled (the cloud-client base image).

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    memory: 1024
    shell: /bin/bash
aws_accounts:
  - name: lab
    services: ["ec2", "iam", "s3"]
    policies: [arn:aws:iam::aws:policy/PowerUserAccess]
    admin_policies: [arn:aws:iam::aws:policy/AdministratorAccess]
bashtrack_scripts/setup-workstation
#!/bin/bash
set -euxo pipefail

aws configure set aws_access_key_id "$INSTRUQT_AWS_ACCOUNT_LAB_AWS_ACCESS_KEY_ID"
aws configure set aws_secret_access_key "$INSTRUQT_AWS_ACCOUNT_LAB_AWS_SECRET_ACCESS_KEY"
aws configure set region us-east-1
GOTCHAS

The policies: field controls what the learner can do. The admin_policies: field controls what setup scripts can do. They are independent. A common bug is to widen policies: to make the learner's check pass, when the right fix was to widen admin_policies: so setup could provision the prerequisite resource.

AWS accounts take 30–60 seconds to provision on top of container boot. Set learner expectations in the loading message.

If your setup script provisions resources for the lesson, do not run those provisioning calls under the learner's identity — the resources show up in the learner's CLI session as "I created this" when in fact setup did. Use a separate profile for admin operations:

bash
aws configure --profile admin set aws_access_key_id ...
aws --profile admin s3 mb s3://lab-bucket-$RANDOM
VARIATIONS

For Azure, see Recipe 8. For GCP, see Recipe 9. For tracks that span two clouds, see Recipe 10.

When the lesson needs the AWS console rather than just the CLI, add a virtualbrowsers block pointing at the AWS console URL, and surface a browser tab — see Recipe 15 for the equivalent shape.

Container plus Azure subscription

InfrastructureIntermediate
Use when The lesson involves real Azure resources — resource groups, virtual machines, storage accounts, AAD — and the learner needs to operate against a real subscription.
PROBLEM

Same shape as Recipe 7 (AWS), but Azure has its own auth model and its own credential injection convention. A track copy-pasted from AWS to Azure without adjusting the auth handshake will appear to work in setup and fail mysteriously in any check that calls az.

SOLUTION

Declare an azure_subscriptions block in config.yml. The platform provisions a service principal scoped to a fresh subscription. Pair with a workstation container running the cloud-client base image. Source the auto-injected env vars and az login with the service principal in setup.

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    memory: 1024
    shell: /bin/bash
azure_subscriptions:
  - name: lab
    roles: [Contributor]
    admin_roles: [Owner]
bashtrack_scripts/setup-workstation
#!/bin/bash
set -euxo pipefail

source /etc/profile.d/instruqt-env.sh

az login --service-principal \
  --username "$INSTRUQT_AZURE_SUBSCRIPTION_LAB_ADMIN_SPN_ID" \
  --password "$INSTRUQT_AZURE_SUBSCRIPTION_LAB_ADMIN_SPN_PASSWORD" \
  --tenant "$INSTRUQT_AZURE_SUBSCRIPTION_LAB_TENANT_ID" >/dev/null

az account set --subscription "$INSTRUQT_AZURE_SUBSCRIPTION_LAB_SUBSCRIPTION_ID"
GOTCHAS

Azure provisions a service principal, not a user. There is no "console password" on the auto-injected variables for the SPN. If the lesson needs the learner to log into the Azure portal, provision a separate user account in the subscription as part of setup.

Sourcing /etc/profile.d/instruqt-env.sh is necessary in any non-login shell that needs the auto-injected variables. Login shells (the default for terminal tabs) source it automatically. Cron jobs, service units, and scripts launched by other scripts may not.

The roles: field uses Azure role names ("Contributor", "Reader") and admin_roles: likewise. There is no "policy" concept at the assignment level the way AWS has.

VARIATIONS

For tracks that need multiple subscriptions in the same tenant, declare multiple azure_subscriptions: entries with different name: values. Each gets its own variable namespace.

For combined AWS+Azure tracks, see Recipe 10.

Container plus GCP project

InfrastructureIntermediate
Use when The lesson involves real GCP resources — Compute Engine, Cloud Storage, IAM, BigQuery — and the learner needs to operate against a real, scoped project.
PROBLEM

Same shape as Recipes 7 and 8, but GCP introduces a wrinkle the other two clouds do not have. The platform provisions both a user identity and an admin service account for the project. Setup scripts often need admin power, but the learner needs to operate as the user. Mixing the two pollutes the learner's gcloud session and produces false-pass check scripts.

SOLUTION

Declare a gcp_projects block. Activate the user credentials in the workstation's setup so the learner's terminal opens already authenticated as the user. For admin operations during setup, use the auth credential override pattern (Recipe 35) to scope admin power to a single command without changing the active session.

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    memory: 1024
    shell: /bin/bash
gcp_projects:
  - name: lab
    services: [compute.googleapis.com, storage-api.googleapis.com]
    roles: [roles/compute.viewer]
    admin_roles: [roles/owner]
bashtrack_scripts/setup-workstation
#!/bin/bash
set -euxo pipefail

PROJECT_ID="$INSTRUQT_GCP_PROJECT_LAB_PROJECT_ID"
USER_KEY="$INSTRUQT_GCP_PROJECT_LAB_SERVICE_ACCOUNT_KEY"
ADMIN_KEY="$INSTRUQT_GCP_PROJECT_LAB_ADMIN_SERVICE_ACCOUNT_KEY"

# Activate user credentials as default
gcloud auth activate-service-account --key-file="$USER_KEY"
gcloud config set project "$PROJECT_ID"

# Provision a starter VM using admin power, without polluting the user session
CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE="$ADMIN_KEY" \
  gcloud compute instances create starter \
    --project="$PROJECT_ID" --zone=us-central1-a \
    --machine-type=e2-small --image-family=debian-12 --image-project=debian-cloud
GOTCHAS

The auto-injected SERVICE_ACCOUNT_KEY is the user-scoped key; ADMIN_SERVICE_ACCOUNT_KEY is the admin key. They are paths to JSON files. Pass them to --key-file= or to CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE as paths.

If a setup script forgets to scope admin operations, the active gcloud session becomes the admin's, and any check that validates "the user can do X" trivially passes. This is the most common false-pass pattern on GCP tracks. See Recipe 35 for the discipline that prevents it.

The services: array enables APIs for the project. Forgetting to enable a service produces "API has not been used" errors at runtime.

VARIATIONS

For private VMs reachable only via IAP tunnel, see Recipe 11. For tracks that span GCP and AWS, see Recipe 10.

For tracks with multiple GCP projects, declare multiple entries with distinct name: values; each gets its own variable namespace and own admin/user keys.

R 10
Part II — Infrastructure

Multi-cloud track wiring

InfrastructureAdvanced
Use when The lesson is about how two clouds interoperate — VPC peering, federated identity, cross-cloud DNS, multi-cloud disaster recovery, or any scenario where the boundary between clouds is part of the story.
PROBLEM

A multi-cloud lesson cannot be taught against one cloud. The standard temptation is to teach "the AWS half" and "the Azure half" as separate tracks and trust the learner to assemble the picture. That works for documentation; it does not work for hands-on labs, because the interoperation is exactly where the lesson lives.

SOLUTION

Declare both cloud account blocks in the same config.yml. The platform provisions both in parallel. A single workstation container holds the CLIs for both clouds. Setup configures both CLIs from the corresponding auto-injected variables. Each cloud has its own variable namespace — there is no cross-namespace collision.

SKELETON
yamlconfig.yml
version: "3"
containers:
  - name: workstation
    image: gcr.io/instruqt/cloud-client
    memory: 1024
    shell: /bin/bash
aws_accounts:
  - name: aws
    services: ["ec2", "iam"]
    policies: [arn:aws:iam::aws:policy/PowerUserAccess]
    admin_policies: [arn:aws:iam::aws:policy/AdministratorAccess]
gcp_projects:
  - name: gcp
    services: [compute.googleapis.com]
    roles: [roles/compute.viewer]
    admin_roles: [roles/owner]
bashtrack_scripts/setup-workstation (excerpt)
aws configure set aws_access_key_id "$INSTRUQT_AWS_ACCOUNT_AWS_AWS_ACCESS_KEY_ID"

InfrastructureAdvanced
Use when The lesson involves a Compute Engine VM that should appear "private" — no public IP — but the learner still needs SSH access and possibly a web UI surface.
PROBLEM

A standard service tab cannot reach a VM that has no public IP and lives in a VPC the platform does not peer with. The naive answer — give the VM a public IP — defeats the lesson, which is usually about working with private resources securely.

Pre-pull Docker images in setup

TechniqueBasic
Use when The track runs Docker containers as part of the lesson, and the first docker run in the lesson takes long enough to feel broken.
PROBLEM

A docker run against an uncached image triggers a layer pull. Pulls of common images — postgres, redis, a vendor's official image — can take 20–60 seconds on the lab's network. The first time the learner runs the command, they wait. The second time, it is instant. The first time is the impression that lasts.

SOLUTION

SKELETON
bashtrack_scripts/setup-workstation

docker pull redis:7-alpine &

wait
GOTCHAS

Pre-pulling makes the lab boot longer. The learner's "still loading" experience is one bucket of time; the "first command takes 30 seconds" experience is a different bucket. Pre-pulling moves time from the second bucket to the first. That is usually the right trade — learners forgive boot time, they do not forgive a frozen prompt.

Part III — Technique

Bootstrap wait

TechniqueBasic
Use when Track-level setup runs commands that require the platform's host agent to be fully initialized — file systems mounted, env vars injected, networking up.
PROBLEM

Track-level setup scripts can fire before all of the host's bootstrap is complete. Commands that touch /etc/profile.d/instruqt-env.sh, that depend on cloud account injection, or that expect specific files in /opt/instruqt/ may fail intermittently because the file or variable is not yet there. The failure mode is "works on the second try" — a sign of a race.

SOLUTION

Wait at the top of every track-level setup script for the platform's bootstrap-completed marker. The platform creates this file when the host is fully ready for user-mode scripts.

SKELETON
bash
#!/bin/bash
set -euxo pipefail

# Wait for the host to finish bootstrapping
until [ -f /opt/instruqt/bootstrap/host-bootstrap-completed ]; do
  sleep 1
done

# … rest of setup …
GOTCHAS

The marker file is the platform's contract. Do not invent your own marker. Other tooling (the agent, monitoring, the platform's own checks) all key off this same file.

Per-challenge setup scripts run after the track-level setup completes, so they do not need the bootstrap wait. Only track-level setup is early enough to hit the race.

A sleep 1 poll is fine. Do not poll faster — the wait is rarely longer than a few seconds, and a tighter loop does nothing but burn CPU.

VARIATIONS

When a setup script needs not just the host but a specific service to be ready (postgres, redis, an external API), the bootstrap wait is the first wait but not the only wait. Add Recipe 22 below it.

R 22
Part III — Technique

Wait-for-port readiness probe

TechniqueBasic
Use when A setup or check script depends on a service being ready to accept traffic on a known port.
PROBLEM

A common race in track setup: launch a service in the background, immediately curl it, and watch the curl fail because the service is still binding the port. The retry-and-eventually-succeed pattern is unreliable; the curl-and-immediately-fail pattern is worse. The script needs to wait for the port specifically, not for "the service" abstractly.

SOLUTION

Loop on a TCP probe until the port responds. Use nc -z for raw TCP, curl -fsS for HTTP. Set a timeout so a misconfigured service does not hang setup forever.

SKELETON
bash
# Wait for any TCP port
wait_for_port() {
  local host="$1" port="$2" timeout="${3:-60}" elapsed=0
  while ! nc -z "$host" "$port" 2>/dev/null; do
    sleep 1
    elapsed=$((elapsed + 1))
    if [ "$elapsed" -ge "$timeout" ]; then
      echo "Timeout waiting for $host:$port" >&2
      return 1
    fi
  done
}

# Wait for an HTTP endpoint
wait_for_http() {
  local url="$1" timeout="${2:-60}" elapsed=0
  while ! curl -fsS "$url" >/dev/null 2>&1; do
    sleep 1
    elapsed=$((elapsed + 1))
    if [ "$elapsed" -ge "$timeout" ]; then
      echo "Timeout waiting for $url" >&2
      return 1
    fi
  done
}

# Usage
wait_for_port db 5432
wait_for_http http://localhost:5000/healthz
GOTCHAS

nc -z checks that the port is open, not that the application is healthy. A web server can have its port open while it is still loading state and returning 503. Use wait_for_http against a /healthz endpoint when health, not just liveness, is what you need.

The default timeout is 60 seconds. Most services are ready in 5–15. A 60-second cap protects against indefinite hangs without being so short that legitimate slow starts trip it.

pg_isready for postgres and redis-cli ping for redis are domain-specific equivalents that report application-level health. Prefer them when the workstation image has them installed.

VARIATIONS

For mutual readiness between services (A waits for B, B waits for A), the wait-for-port pattern composes with Recipe 34 (agent variable hand-off) so that one host can signal another that it is ready, breaking the cycle.

TechniqueBasic
Use when Setup needs to launch a long-running process (a web server, a background worker, a watchdog) that should outlive the setup script.

SOLUTION

SKELETON

Part III — Technique

Helper Python module for tests

TechniqueIntermediate
Use when A track has many check or solve scripts that share validation logic, and the per-script bash is starting to drift in subtle ways.
PROBLEM

The first three check scripts in a track are bash. By the tenth, they have copy-pasted the same "does this file exist," "is this string in the file," "does this command return zero" idioms five times each. Each copy is slightly different, because the author tweaked one and forgot to update the others. The tests no longer test what you think they test.

SOLUTION

Write the shared logic once as a Python module, install it in a system-wide location during track setup, and import it from each check or solve script. The check script becomes one or two lines of "import and assert" rather than bespoke bash.

SKELETON
bashtrack_scripts/setup-workstation (excerpt)
mkdir -p /usr/lib/python3/dist-packages
cat > /usr/lib/python3/dist-packages/instruqt_tests.py <<'EOF'
import subprocess, os, sys

def fail(msg):
    print(msg, file=sys.stderr)
    sys.exit(1)

def assert_file(path):
    if not os.path.isfile(path):
        fail(f"Expected file not found: {path}")

def assert_contains(path, needle):
    assert_file(path)
    if needle not in open(path).read():
        fail(f"Expected '{needle}' in {path}")

def assert_command(cmd, rc=0):
    r = subprocess.run(cmd, shell=True, capture_output=True)
    if r.returncode != rc:
        fail(f"Command failed: {cmd}\nstdout: {r.stdout.decode()}\nstderr: {r.stderr.decode()}")
EOF

assert_command("curl -fsS http://localhost:3000/")
EOF
GOTCHAS

The dist-packages path is Debian/Ubuntu-specific. On other distributions, use /usr/local/lib/python3.X/site-packages/.

Keep the helper module small. Once it grows past 150 lines, the track has acquired a hidden test framework, and that framework will start to need its own tests.

VARIATIONS

Part III — Technique

Idempotent binary wrapper

TechniqueBasic
Use when A setup script needs to wrap a system binary — to add flags, intercept arguments, or enforce a sandbox mode — and the script may run more than once.
PROBLEM

The standard pattern for wrapping a binary is to rename the original out of the way, then write a shell script in its place that calls the renamed original with extra arguments. This works perfectly the first time. On the second run, the rename moves the wrapper to the backup path, and the new wrapper ends up calling itself — infinite recursion that fills the host's process table before anything else gets a chance to run.

SOLUTION

Guard the rename. Only move the original out of the way if it has not already been moved.

SKELETON
bash
#!/bin/bash
set -euo pipefail

# Only rename if the real binary hasn't already been moved
if [ ! -f /usr/bin/chromium-real ]; then
  mv /usr/bin/chromium /usr/bin/chromium-real
fi

# Write (or overwrite) the wrapper
cat > /usr/bin/chromium <<'EOF'
#!/bin/bash
exec /usr/bin/chromium-real --no-sandbox "$@"
EOF
chmod +x /usr/bin/chromium
GOTCHAS

The wrapper itself is safe to rewrite on every run — the danger is only in the rename. Putting the rename behind the [ ! -f ] guard is the entire fix.

If the original binary is a symlink rather than a file, [ ! -f ] still works because -f follows symlinks, but mv will move the symlink itself. If you need the underlying target moved instead, resolve first with readlink -f.

VARIATIONS

This pattern composes with anything that needs an idempotent overwrite-once: replacing a config file, swapping a default editor, or substituting a library. The same [ ! -f <backup> ] guard pattern applies in each case.

Part III — Technique

Profile.d + .bashrc dual-write

TechniqueBasic
Use when You want an environment variable to be available in every shell the learner opens — including login shells, non-login interactive shells, and shells launched from inside a code tab's terminal.
PROBLEM

/etc/profile.d/*.sh is sourced by login shells. The user's ~/.bashrc is sourced by interactive non-login shells. Some shells the learner opens are one, some are the other, and the difference is not predictable from the lesson's perspective. A variable written only to one of the two will appear and disappear depending on how the shell was started.

SOLUTION

Write the variable to both. /etc/profile.d/instruqt-env.sh for system-wide login shells; ~/.bashrc for interactive non-login shells. The variable is available everywhere; the cost of the duplication is a few lines in setup.

VARIATIONS

For zsh users — uncommon on Instruqt but possible on custom images — write to /etc/zsh/zshenv and ~/.zshrc in addition to or instead of the bash files.

Part III — Technique

Defensive challenge-level setup

TechniqueBasic
Use when A challenge's setup creates a resource (a file, a user, a database row), and you want the setup to survive being run multiple times — including running on top of a state where the resource already exists.
PROBLEM

The platform may run a challenge's setup more than once. The learner can use the "Restart this challenge" button. The author may run a setup script during testing several times in a row. A setup script that calls useradd iggy twice fails the second time with "user already exists." A setup that runs INSERT INTO ... twice produces duplicate rows.

SOLUTION

Query before you create. The pattern is "if-exists, skip; if-absent, create." For users, id <user> 2>/dev/null || useradd .... For files, [ -f <path> ] || cat > <path> .... For database rows, INSERT ... ON CONFLICT DO NOTHING.

SKELETON
bash02-add-a-user/setup-workstation
#!/bin/bash
set -euxo pipefail

# User: skip if it exists
if ! id iggy >/dev/null 2>&1; then
  useradd -m -s /bin/bash iggy
  echo "iggy:lab-pass" | chpasswd
fi

# File: skip if it exists
if [ ! -f /home/iggy/.config/app.yaml ]; then
  mkdir -p /home/iggy/.config
  cat > /home/iggy/.config/app.yaml <<'EOF'
mode: lab
EOF
  chown -R iggy:iggy /home/iggy/.config
fi

# Database row: ON CONFLICT
psql "$DATABASE_URL" <<'EOF'
INSERT INTO users (email, role) VALUES ('iggy@example.com', 'admin')
ON CONFLICT (email) DO NOTHING;
EOF
GOTCHAS

Idempotence is not the same as "safe to run twice." A setup that removes a file or row to prepare a clean state is also legitimate, but it must do so unconditionally: rm -f <path> is idempotent, rm <path> errors on the second run when the file is already gone.

useradd -f does not mean "force create even if exists." The standard idempotence idiom for useradd is the id <user> || guard, not a flag.

VARIATIONS

For setup that runs a long-running operation conditionally, use a sentinel file: [ -f /var/lib/seeded ] || (seed-schema && touch /var/lib/seeded). The file's existence is the marker that the work has happened.

TechniqueBasic
Use when The challenge has a solve script, and the lab's testing flow may invoke solve more than once on the same host.

If the learner clicks Solve, then clicks Restart, then clicks Solve again, the script runs against a host where it has already partly run. SKELETON

Agent variable cross-host hand-off

TechniqueIntermediate
Use when A value generated on one host needs to be readable on another — typically a generated password, a provisioned IP, or a key that one host creates and another consumes.
PROBLEM

Hosts in a track do not share file systems. There is no /shared/ between containers; environment variables set in one are not visible in the other. The learner can copy values manually between terminal tabs, but lifecycle scripts cannot. The platform's answer is the agent variable store.

SOLUTION

agent variable set KEY VALUE on one host writes the value to a per-session key-value store. agent variable get KEY on any other host reads it. The store is scoped to the session — values are gone at lab teardown. The get call blocks until the variable is set, making this an implicit synchronization mechanism between hosts.

SKELETON
bashtrack_scripts/setup-host-a

# Use it

GOTCHAS

agent variable get blocks until the variable is set. Use this property deliberately; it makes the hand-off correct without explicit waits.

Once a variable has been read by agent variable get, it is also injected as an environment variable in every subsequent shell on that host. The learner can echo $DB_PASSWORD from a terminal tab. If the value should not be exposed to the learner, set it without ever calling get on the host the learner uses.

CLOUDSDK auth credential override

TechniqueIntermediate
Use when A GCP setup script needs admin power for one specific operation, but the learner's gcloud session must remain authenticated as the user.
PROBLEM

By the time the learner opens a terminal, they are implicitly the admin, which means any check script that validates "the user can do X but cannot do Y" produces a false pass.

Use the CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE environment variable. Setting it before a single gcloud call activates the named credential file for that one command only, without changing the active session. The user's session stays clean.

SKELETON

gcloud auth revoke to "undo" sounds like an alternative but is not. Revoke removes the credential entirely; the active session falls back to "no auth at all."

For other tools that talk to GCP — Terraform, kubectl with a GCP plugin — the override variable does not always apply. Use tool-specific equivalents for everything else.

VARIATIONS

Granular check messaging

TechniqueIntermediate
Use when A challenge has multiple independent things the learner must do, and a single pass/fail message cannot meaningfully tell them which one is missing.
PROBLEM

The default check pattern is binary: pass or fail, with one fail-message. For a challenge with one assertion, that is fine. For a challenge with five assertions, "Something is wrong with your work" is useless feedback. The learner re-checks every assertion themselves, which defeats the purpose of the check.

SOLUTION

Test each assertion independently, accumulate failures, and emit a specific remediation hint for each one that fails. Exit non-zero only after surfacing every failed assertion.

SKELETON

#!/bin/bash
fails=0

check() {
  local desc="$1"
  shift
  if "$@"; then
    echo "✓ $desc"
  else
    echo "✗ $desc — $REMEDY"
    fails=$((fails + 1))
  fi

REMEDY="Create the file /home/iggy/project/handler.py"

set -e is the wrong default for granular checks. With -e, the first failed assertion exits the script and you lose the rest. Keep the script with default error handling, accumulate explicitly, exit at the end.

Each assertion should be cheap. Granular checks run on every Check-button click; a 30-second check that runs 5 times in a session adds up to wasted time.

VARIATIONS

For lessons that grade work on a curve (multiple correct answers, partial credit), use the granular pattern with a counter and report a percentage. See Recipe 37 for the full scored-rubric shape.

A Closing Note

A cookbook is a strange genre. It is built to be useful one page at a time, and most of the time that is how it gets used — opened to a recipe, copied, adapted, closed. But a cookbook read end to end has a second life. The arrangement of the recipes, the throughlines that keep showing up, the patterns between the patterns: those are the working theory of the craft.

The throughlines, after 47 recipes

IDEMPOTENCE IS THE PRICE OF ADMISSION

Half the technique recipes are about making setup, solve, and check scripts survive being run twice. The platform offers retry buttons; learners use them; an author who does not write idempotent scripts is shipping a track that breaks for the second-attempt learner. Once the discipline is internalized, the cost of writing idempotent code is roughly zero. Once it is not, the bugs are perpetual.

THE LEARNER'S BROWSER IS NOT ON YOUR NETWORK

Three of the infrastructure recipes (12, 14, 25) and at least one technique recipe (22) have gotchas that boil down to "the learner's browser cannot resolve internal Docker hostnames." Relative paths, the platform proxy, service tabs versus website tabs — they all live in this constraint. Build the mental model once and you will stop tripping over it.

FAILURE MESSAGES ARE CONTENT

Six of the author recipes touch failure messaging directly or indirectly. The check script's stdout on failure is the moment the learner is most receptive to teaching, because they have just realized they do not know something. Authors who treat that moment as a UX surface ship better tracks than authors who treat it as exit code 1.

SMALL FILES ARE BETTER THAN BIG REPOS

Heredoc-based generation (Recipe 24), inline reference implementations (Recipe 31), file-based quiz answers (Recipe 43) — the pattern is the same: keep the thing inside the track, do not reach across the network for it. Reduces dependencies, simplifies review, makes the track portable. The exception is genuinely large project trees, where the cost of the heredoc grows past the cost of the dependency.

COMPOSITION IS THE RULE, NOT THE EXCEPTION

Almost every recipe in the book references another recipe in its Variations section. The patterns compose: container-plus-postgres (Recipe 14) uses wait-for-port (Recipe 22) and background launch (Recipe 23) and granular checks (Recipe 36). Real tracks use eight or ten patterns at once. The book is organized as discrete recipes for discoverability; the practice of building tracks is a chord, not a melody.

A few last observations

The recipes here are a snapshot. The platform evolves; the products being demonstrated change; new patterns emerge as new problems are encountered. The way to keep the book useful is to add to it. When you find a pattern that has not been written down yet, write it down — even as an internal note. The cumulative library is what keeps an author's velocity high across years of tracks.

The recipes are also opinionated. Reasonable authors will disagree with some of the calls — the choice of FastAPI over Flask, the preference for heredocs over external repos, the recommendation to default to a 70% rubric threshold. Disagreement is fine; the point of an explicit recipe is to make the choice visible so it can be argued about. An anti-pattern is just a pattern someone has decided not to use.

THE AUTHOR'S MAXIM

Build well. Test honestly. Ship deliberately. Maintain with patience. The patterns will not catch every problem — but they will catch enough of them that you can spend your attention on the ones that matter.
